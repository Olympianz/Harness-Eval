# Harness Eval 实验台操作手册与底层原理

**面向 Trace 诊断、Dataset 构建和版本回归的实操指南**

适用版本：2026 年 9 月私有实验台。访问地址：由项目所有者提供私有访问地址。

这份手册的前半部分让你从虚构 Trace 完整走一遍标注与回归；后半部分解释评测系统为什么要保存轨迹、怎样把运行记录变成稳定样本，以及指标、归因和发布门禁的边界。它既是当前实验台的说明书，也是下一步实现真实 Harness Eval 的设计依据。

当前实验台是离线交互原型：它接收已脱敏的结构化 Trace，由人维护预期与成功标签，在浏览器中计算指标；它不会执行 Agent、调用模型或自动判分。所有导入与修改的数据保存在当前浏览器的 localStorage。原始私有部署仅对所有者开放；重新部署时需要单独配置访问控制，但浏览器存储不是团队数据库或备份。

## 1 十分钟完成一次完整体验

1. 打开私有网址，进入「Trace 观察」。默认有 6 个虚构 case，每个 case 各有一条 v1 基线和 v2 候选 Trace，共 12 条。
2. 点击 TR-102「查询版本变更」。观察六阶段轨迹：意图识别正确，但 release_lookup 没有触发，转而使用 web_search。
3. 在右侧检查预期与实际 Skill、Tool；首要失败阶段选 Skill，失败类型选「漏触发」，在备注写证据及修复假设。确认「纳入 Dataset」后点「保存标注」。
4. 进入「Dataset 构建」，找到 C-02 的 v1 和 v2 样本。点击可修订标签；点击「导出数据集」得到 JSONL 文件。
5. 进入「Eval 与回归」，选择 v1 基线与 v2 候选。观察 Trigger Precision/Recall、Tool Accuracy、成功率、平均 Token、平均 Latency 和逐 case 变化。
6. 返回 TR-102，临时关闭「纳入 Dataset」并保存。再次进入 Eval：C-02 从配对集合中消失，配对数和指标立即变化。体验完可点「重置示例」恢复。

建议第二次体验 TR-104：工具名 calculate_price 选对了，但少传 billing_period；该条任务失败，当前 Tool Accuracy 仍把它计为工具选择正确。这正好说明「工具选择准确」与「工具参数准确」是两种不同指标。

## 2 页面和数据的基本概念

| 概念 | 含义 | 在实验台中的对应 |
| --- | --- | --- |
| Case | 同一个测试任务及其预期；跨版本保持相同 ID | caseId，如 C-02 |
| Trace | 某版本执行一个 case 的一次记录 | id，如 TR-102，含 steps 和成本 |
| 标注 | 对预期、成功与失败原因作人工判断 | 右侧检查器的可编辑字段 |
| Dataset | 被选入评测的 Trace 集合 | inDataset 为 true 的记录 |
| 回归配对 | 同一 case 在两个版本下各取一条记录 | 按 caseId 对齐后比较 |

Trace 是「发生了什么」，Dataset 是「哪些任务值得反复测、什么算对」。真实平台应把 case 的预期与 trial 的运行结果分别存储；当前原型为方便探索，把两者放在同一条 Trace 内。

### Trace 观察

- 列表可按 ID、case、任务标题或输入搜索；可筛选全部、失败、已标注、Dataset 内。
- 点击一行打开检查器。上方展示任务输入、版本、Token、Latency；中间是六阶段的观察记录；下方可修订预期与实际字段、最终成功状态和失败标签。
- 导入记录可以没有 steps；此时仍可依据外部记录标注，但阶段诊断的证据更弱。

### Dataset 构建

- 「纳入 Dataset」是显式开关。关闭后 Trace 仍留在观察列表，但不再参与 Eval。
- 导出格式为 JSONL，每行一个完整 Trace 对象，包含输入、预期、实际、steps、标注和版本。请自行保管导出文件。

### Eval 与回归

- 必须选两个不同版本；系统只比较 Dataset 内 caseId 相同的样本。若版本没有配对 case，会显示空状态。
- 面板显示六项汇总指标、首要失败阶段分布、已修复与退化数量，以及逐 case 的结果、Token 和 Latency 差异。

## 3 导入脱敏 Trace

### 支持的输入和限制

点击「导入 Trace」，可以粘贴单个 JSON 对象、JSON 对象数组或逐行 JSONL；也可选择 .json、.jsonl、.ndjson 文件。文件上限 5 MB；一次最多 2,000 条。导入前应在外部完成脱敏。重复的 Trace id 会被拒绝，未提供 id 时会自动生成一个临时 ID。

| 字段 | 类型 | 用途与规则 |
| --- | --- | --- |
| id | 字符串，可选 | 单次运行唯一标识；重复时不能导入 |
| caseId | 字符串，必填 | 跨版本配对的任务 ID；同一任务必须一致 |
| version | 字符串，必填 | 版本名称，供下拉框选择，区分大小写和空格 |
| title, input | 字符串，必填 | 任务标题和脱敏用户输入 |
| expectedSkill, predictedSkill | 字符串，必填 | 预期与实际 Skill；空字符串表示不需要或未触发 |
| expectedTool, predictedTool | 字符串，必填 | 预期与实际工具名；当前按完全相等计分 |
| success | 布尔，必填 | 任务最终结果，由导入数据或人工给定 |
| tokens, latency | 非负数字，必填 | Token 数与秒数，当前计算算术均值 |
| steps | 数组，可选 | stage、observation、status；用于阅读过程 |
| failureStage, failureType, note | 字符串，可选 | 人工失败归因；未填表示未标注 |
| inDataset | 布尔，可选 | 仅 true 会直接纳入 Dataset，默认 false |

### 最小可导入样本

```json
{
  "id": "TR-901",
  "caseId": "C-91",
  "version": "v1 baseline",
  "title": "虚构套餐报价",
  "input": "比较 A 和 B 的年度费用",
  "expectedSkill": "pricing_compare",
  "predictedSkill": "pricing_compare",
  "expectedTool": "calculate_price",
  "predictedTool": "calculate_price",
  "success": false,
  "tokens": 1800,
  "latency": 8.2
}
```

粘贴成功后进入 Trace 列表，打开新记录，补充失败阶段、类型和依据，再开启「纳入 Dataset」。若要比较候选版本，另外导入相同 caseId、不同 version 的一条记录。

### 导入前的质量检查

- 同一 caseId 是否真的代表同一输入、同一预期和同一外部环境？若参考资料或工具状态已变，应记录基准版本，必要时另建 case。
- Token 是否为同一统计范围（只算模型输入输出，还是包含所有子 Agent）？Latency 是否为同一开始和结束时点？
- success 是否有证据支持？「Agent 自称完成」不等于外部状态真的改变。
- 脱敏是否覆盖正文、工具参数、返回值、文件名、URL、异常堆栈和 metadata。

## 4 如何给六个阶段标注失败

首要失败阶段应指向最早导致任务偏离目标、且能从 Trace 证据确认的环节。一个阶段出错会让下游多个阶段表现异常；备注中可写次生问题，避免把一个根因重复统计多次。若证据不足，保留未标注并说明缺失信息，不要强行归因。

| 阶段 | 需要回答的问题 | 典型证据 |
| --- | --- | --- |
| 意图 | 是否理解用户要做的事、约束及不该做的事？ | 将「求和」理解成「创建日程」 |
| 规划 | 步骤、依赖、并行与重规划是否覆盖目标？ | 漏掉先查规则再计算，或过早执行 |
| Skill | 是否触发正确能力、是否漏触发或误触发？ | 应触发 release_lookup，实际未触发 |
| Tool | 工具选择、参数、执行及错误恢复是否正确？ | 选中 calculate_price，但漏 billing_period |
| 聚合 | 是否正确整合多个步骤或子 Agent 的结果？ | 三个结论中一条没有对应来源 |
| 验证 | 是否复核结果、来源和外部状态，发现错误？ | 缺失引用却通过最终检查 |

TR-102 可标为 Skill 漏触发；TR-104 虽然最终答案也错，但最早可定位的问题是 Tool 参数错误；TR-105 的首要问题是聚合时漏来源，验证未拦截是后续防线失效。真实系统可以同时保存 primary_stage、secondary_stages 和证据跨度。

当前失败类型菜单有误触发、漏触发、路由错误、参数错误、执行失败、计划偏离、结果不完整、校验遗漏、其他。它是教学用的横向标签，未强制绑定某个阶段；生产系统应定义更严格的阶段×错误码矩阵和标注准则。

## 5 当前指标的准确口径

以下公式直接对应当前页面代码。所有版本对比指标都先取 Dataset 内按 caseId 成功配对的样本，再分别计算两个版本；它们不是所有导入 Trace 的全量统计。空分母显示「—」。

| 指标 | 计算方式 | 容易误解的地方 |
| --- | --- | --- |
| Trigger Precision | TP / (TP + FP) | TP 为非空预期 Skill 与实际 Skill 相同；实际非空且不等于预期记 FP |
| Trigger Recall | TP / (TP + FN) | 预期非空且与实际不等记 FN；错误路由到另一 Skill 可同时贡献 FP 和 FN |
| Tool Accuracy | 预期工具名 = 实际工具名的配对样本数 / 配对样本数 | 只比较名称，不检查参数、执行结果或多工具序列 |
| 成功率 | success=true 的配对样本数 / 配对样本数 | success 是导入或人工维护的标签，没有自动真值校验 |
| 平均 Token | 配对样本 tokens 总和 / 配对数 | 算术均值，不是 P50/P95，也未分输入输出或子 Agent |
| 平均 Latency | 配对样本 latency 总和 / 配对数 | 单位为秒；没有冷启动和并行关键路径拆解 |

其中 TP 是正确触发，FP 是实际触发但与预期不同，FN 是应触发却没有触发正确 Skill。例如错误触发另一 Skill：对于被错误选中的 Skill 是 FP，对于应选中的 Skill 是 FN。当前原型把正确具体 Skill 名当作 TP，而不是仅把「触发了某个 Skill」当作 TP。

页面中的百分比差值用百分点 pp，例如成功率从 33% 到 83% 是约 +50 pp，而不是「增长 50%」。Token 和 Latency 的差值是候选减基线；负值表示更省或更快。

### 用默认样例核对

全部 6 个 case 均在 Dataset 时，基线成功 2/6，候选成功 5/6；基线 Skill TP=4、FP=1、FN=1，所以 Precision=80%、Recall=80%。基线 Tool 名称匹配 4/6；候选工具名称匹配 6/6。TR-104 的 v1 虽被计入工具名称匹配，但其任务失败，因为参数错误。页面显示数值经过四舍五入，不能代替原始计数。

## 6 回归比较的配对逻辑

系统先按 version 过滤 Dataset，再对每条基线 Trace 查找候选版本中第一个相同 caseId 的 Trace。只有找到双方记录的 case 才进入统计。故不要在同一版本给一个 caseId 放入多条记录并期待系统计算重复试验均值；当前实现只拿第一条匹配。

| 基线 | 候选 | 页面结论 |
| --- | --- | --- |
| 失败 | 成功 | 已修复 |
| 成功 | 失败 | 退化 |
| 成功 | 成功 | 持平 |
| 失败 | 失败 | 持平，但可能仍需修复 |

「持平」只表示 success 的布尔状态未变化，不能推断答案质量、根因或成本没有变化。C-05 在两版都失败，但 Token 和 Latency 可下降；这不能冲抵核心功能失败。

正式回归还应固定模型版本、Prompt/Skill/Tool 版本、工具返回快照、知识版本和执行环境。随机性较高的任务需对同一 case 重复运行，报告均值、离散度与置信区间；一次成功或失败不能当成稳定能力。

## 7 从 Trace 到 Dataset 的底层原理

### 7.1 三层对象

| 层 | 回答的问题 | 建议保存 |
| --- | --- | --- |
| Case | 要测试什么，什么算成功？ | 输入、约束、预期、断言、风险级别、来源与版本 |
| Trial Trace | 某次实际发生了什么？ | 版本、事件/Span、工具参数与返回、输出、耗时、Token、外部状态 |
| Grade | 按哪套规则得出什么判断？ | grader 版本、得分、证据、人工复核、置信度 |

在真实 Agent 系统里，一个 Trace 是一次端到端操作，内部可有嵌套 Span，分别记录模型生成、工具调用、交接和校验；多个 trial 可以对应同一个 case。[1][2] 当前实验台用一个扁平 Trace 对象及六个 steps 近似表达。六阶段是分析视角，不代表所有 Agent 都严格依次执行一次：规划可重做，工具可循环，Skill 可能嵌套，验证可能在中途发生。

### 7.2 把海量运行记录变成可评测数据

1. 采集：为每个请求打 traceId、case 候选键、时间、模型与 Harness 版本，记录关键 Span 与最终外部状态。
2. 清理：去重、脱敏、剔除损坏轨迹与不可复现的环境错误；保留失败和异常成功的证据链。
3. 分层抽样：按任务类型、难度、用户群、工具、失败阶段、版本和时间窗口选择代表样本；同时加入稀有高风险、边界和对抗样本。不要只抽高频成功请求。
4. 聚类与提案：用规则、相似度或模型把近似任务归组，生成候选 case 和可能的失败类型；这些只是候选，需人工确认。
5. 标注：业务专家确认输入、可接受结果、应触发的能力、必要的工具/参数、最终状态断言和失败证据。不同意见需仲裁并留记录。
6. 冻结：给 case、参考资料、标注准则、grader 和 Dataset 打版本；拆分开发集、回归集与保留集，防止把评测答案写回 Prompt 或 Skill。
7. 回流：上线后继续从新失败和异常成功中补样本，定期复核过期真值、标签一致性和样本分布。

一百万条 Trace 不意味着一百万条 Dataset 行。日志是行为总体，Dataset 是经过去重、抽样、定义预期与质量审核的任务集。保留 traceId 的可追溯关系，才能从指标钻回失败现场。OpenAI 的评测实践也强调代表性数据、人类反馈校准和持续评测。[3]

## 8 Harness Eval 实际评测的两条链

### Agent Harness 运行链

用户输入和上下文进入 Agent Harness。模型或确定性流程识别意图，选择 Skill，规划步骤，调用 Tool，处理返回和异常，聚合结果并验证，然后把答案或外部状态交付。Harness 负责给模型可行动的环境、边界和反馈；模型本身只是一部分。

### Eval Harness 检验链

Eval Harness 从固定 Case 集合读取输入与环境快照，运行一个或多个 Agent Harness 版本，捕获每次 Trial Trace，再用确定性断言、状态检查、人工或 LLM Rubric 判分，最后按 case、版本和人群聚合，对差异做统计与归因。Anthropic 明确区分了这两种 Harness，并指出评测的是模型与 Agent Harness 的组合。[4]

这两条链不能混同：当前网站属于 Eval 工作台的观察、人工标注和聚合部分，不包含受控重放执行器、自动 Grader、真实工具隔离环境或持续集成任务。因而它能帮助定义评测方案，不能宣称已自动评测一个真实 Agent。

### 为什么要同时看过程和结果

最终结果告诉你用户目标是否完成；过程 Trace 告诉你为何完成或失败。若答案正确但调用了不必要的昂贵工具，结果分数可能好、成本分数差。若调用路径不同却同样达成目标，过于刚性的固定步骤 Grader 可能错判。因此先以最终状态和用户价值为主，再把 Skill、Planning、Tool 等阶段指标用于诊断。[4]

## 9 评测器与指标体系的进阶设计

| 评测层 | 可执行的检查 | 适用 Grader |
| --- | --- | --- |
| 意图 | 目标、限制、禁止行为是否提取正确 | 结构化真值 + 人工复核 |
| 规划 | 关键依赖覆盖、计划到行动一致、重规划是否必要 | 规则 + 针对性 Rubric |
| Skill | 正确 Skill 的触发、漏触发、误触发、冲突 | 多类混淆矩阵 |
| Tool | 选择、参数 Schema、业务约束、执行与恢复 | 代码断言 + 状态检查 |
| 聚合 | 来源覆盖、数值一致、跨子任务信息完整 | 规则 + LLM Rubric |
| 验证 | 是否发现错误、是否阻止错误发布 | 规则 + 人工抽检 |
| 端到端 | 最终任务成功、人工介入、Token、Latency、外部副作用 | 环境状态 + 汇总 |

优先用确定性 Grader 检查 Schema、算术、引用存在性、外部状态和工具参数；开放式质量可用分项 LLM Rubric，给出证据和「无法判断」选项，并用专家标注集持续校准。人工审查处理高风险或意见不一致的样本。不要把一个总分替代各层失败诊断。[4][5]

建议补充当前原型尚无的指标：Skill Collision、Instruction Adherence、Plan Coverage、Plan→Action Alignment、Replan Rate、Tool Argument Accuracy、Execution Error、Recovery Accuracy、Source Coverage、人工介入次数、P50/P95 Latency、每成功任务成本。每个指标都要写明分母、排除项、任务分层与采集方式。

高成功率不一定代表高质量：样本偏易、参考答案泄漏、人工提前纠错、结果伪成功、只统计有配对的 case，都可能抬高数值。质量和成本应双看；降低 Token 但引入高风险失败不应通过门禁。

## 10 从实验台升级到可复现的平台

| 优先级 | 补齐能力 | 为什么需要 |
| --- | --- | --- |
| P0 | Case 与 Trial 分表；导入适配器；真值和标注版本 | 防止把同一记录的预期和输出混写，支持复用 |
| P0 | 真实 Span 采集、脱敏、权限和审计 | 还原工具参数、调用顺序、成本与外部状态 |
| P0 | 受控执行器和可重放工具环境 | 对同一 case 重跑不同版本，排除环境噪声 |
| P1 | 多层 Grader、人工复核、标注一致性 | 从手工 success 走向可解释判分 |
| P1 | 重复 Trial、分层统计和置信区间 | 面对随机性，避免小样本误判 |
| P1 | CI 回归门禁与失败样本回流 | 每次 Prompt/Skill/Tool 变化都可检测退化 |
| P2 | 团队数据库、共享权限、Dataset 生命周期 | 跨浏览器协作、备份与历史追溯 |

门禁示例：关键任务成功率不能低于基线；高风险 case 不得新增严重退化；Tool 参数错误率不得上升；Token 与 P95 Latency 在预算内。阈值必须在足够样本、稳定环境和可复核真值的前提下设置，不能直接拿当前六个虚构 case 做发布判断。


## 11 常见问题和排查

| 现象 | 原因与处理 |
| --- | --- |
| 导入提示字段错误 | 核对必填字符串、布尔 success、非负数字 tokens/latency；JSONL 应一行一个 JSON 对象 |
| 导入提示 ID 重复 | 给新运行生成唯一 id；同一 case 的不同版本共享 caseId，不共享 Trace id |
| Eval 没有配对 | 检查两个版本不同、caseId 完全一致，且双方都已纳入 Dataset |
| 修改后指标没变化 | 可能该 Trace 未纳入 Dataset，或无配对；也可能改的是不参与该指标的字段 |
| Tool Accuracy 高但成功率低 | 检查参数、执行错误、聚合、验证；当前 Tool Accuracy 仅比较名称 |
| 换设备后数据消失 | 数据只在原浏览器 localStorage；先导出 JSONL，再在新浏览器导入 |
| 点击重置后自定义内容消失 | 重置覆盖当前浏览器的导入和标注；需要保留时先导出 |
